## 질문의 답: 신호와 그 이후 결과는 별개

정합성 검사를 통과한 전체 종목 이력에서 공개된 조건으로 신호를 찾고, 확인일부터 이후 결과를 붙인다. 상승 신호 뒤 하락한 사례도 남는다. 다만 모양만 보는 규칙과 선행 추세·후속 확인 봉까지 필요한 규칙은 구별해야 한다. 품질 격리·결과 관찰 기간 부족 역시 별도 기준이다.

규칙별 최대 150개 화면 예시는 종목·날짜를 분산해 고르며 결과 수익률로 선택하지 않는다. 통계는 그 150개가 아니라 전체 검출 중 20봉 관측을 마친 사례를 사용한다. 최종 골든크로스 예시 150건은 상승 69·하락 79·보합 2건이다. 이 비율은 전체 집계나 무작위 표본의 추정치가 아니다.

`tests/recovery.test.mjs`에서 같은 상승 장악형 뒤의 차트를 상승·하락으로 각각 바꿔도 둘 다 검출되고, 모든 결과의 부호를 뒤집어도 예시 선택 날짜가 같음을 확인한다.

## 복구 원칙

정책 `dual-source-local-scale-v2`는 다음 조건을 코드로 적용한다.

1. 공급자 원문과 요청 URL·수집 시각·SHA-256을 보존한다. Yahoo quote를 기본 가격 단위로 삼는다. 응답 형식·티커·통화·중복 날짜를 검증한다.
2. 대조 봉은 OHLC 범위·날짜·거래량 검사에 통과해야 한다. Naver에도 1원 범위 오류와 무거래 표시가 있어 통째로 교체하지 않는다.
3. 주변 ±60개 날짜 안에서 양쪽 공급자가 일치하는 봉을 찾는다. 일반 구간은 앞뒤 각각 최소 3개, 합계 최소 8개가 필요하다. 이력 양끝 8개 날짜 안에서만 한쪽 최소 8개를 허용한다.
4. 가격 배율은 그 주변 봉들의 OHLC 비율로 확인한다. 가격 일치 허용 폭은 2원 또는 0.01% 중 큰 값, 주변 배율 안정성은 0.02%다. 이는 공급자 반올림 차이 비교용이며 오류 가격을 상·하한에 끼워 맞추는 규칙이 아니다.
5. 거래량 배율은 Yahoo 분할 이벤트의 이후 누적 비율이다. 주변 실제 거래량도 그 배율과 일치해야 한다(허용 폭 2주 또는 0.1% 중 큰 값). 주식배당·분할·기업분할 등의 기준 차이를 확인 못하면 추정 복구하지 않는다.
6. 일반 오류 봉은 당일 OHLC 중 최소 2개도 단위 변환 후 일치해야 한다. 완전 결측 또는 거래량 0·OHLC 동일 채움 봉은 당일 대조가 불가능하므로 유효한 Naver 실거래 봉과 주변 단위 검증으로 복원한다. 모든 변경에 전후 값·배율·대조 날짜를 기록한다.
7. Yahoo 거래량 0과 Naver 거래량 0·시고저 0이 동시에 확인되면 계산용 이력에서 제외한다. Naver 행 부재만으로 휴장을 추정하지 않는다. 예외적으로 공식 공지로 확인한 2015-08-14 휴장 표시 71봉을 제외했다. 나머지 1,189봉은 양 공급자의 무거래 표시가 확인된 경우다.
8. 복구되지 않은 오류·결측·확인 불가능한 0 거래량·명확한 공급자 가격 불일치는 종목 전체를 격리한다. 오류 날짜를 삭제해 숨기지 않는다. 위 무거래 표시 제외와 구별한다.

2015-08-14 증권시장 휴장은 [금융위원회 안내(정책브리핑)](https://www.korea.kr/news/policyNewsView.do?newsId=148799089)로 확인했다. 임의 휴장일 목록이나 전체 거래소 달력을 검증한 것은 아니다.

자료 정정에는 대상 날짜 이후의 대조 봉을 쓰기도 한다. 이는 사후 정정한 학습 자료이며 **그 당시 이용 가능했던 실시간 데이터의 재현본이 아니다.** 신호 탐지의 확인일 이후 결과를 미리 보는 문제와는 다른 층위지만, 당시 실행 가능 전략의 검증이라고 주장하면 안 된다.

## 재현과 검증

```powershell
node tools/recover-data.mjs --check
node tools/build-patterns.mjs --date=2026-09-23 --check
node --test tests/learning.test.mjs tests/pattern-integrity.test.mjs tests/recovery.test.mjs
```

복구 `--check`는 원본 백업과 보존 원문으로 92종목·인덱스·보고서를 다시 만들고 바이트 비교한다. 네트워크 호출이나 파일 수정은 하지 않는다. 빌드 `--check`는 57개 패턴과 품질·인덱스 생성물을 비교한다. 단위·회귀 테스트는 36개다.

실행 결과: 36개 테스트 통과, JS/MJS 40개와 PowerShell 수집 보호 코드 문법 검사 통과, 두 재현 검사 불일치 0건. Browser 스킬로 홈의 복구 안내와 뷰어의 격리 경고를 1280/768/375px에서 확인했다. 문서 전체의 가로 넘침은 없었고, 복구된 삼성전자와 격리된 삼성바이오로직스의 안내·차트 표시를 확인했다. 이 화면 점검은 데이터 내용 전체의 정확성 검증을 대체하지 않는다.

수집은 `node tools/collect-recovery.mjs --provider=naver` 또는 `--provider=yahoo`로 원문만 저장한다. 이미 보존된 응답은 재다운로드하지 않으며 해시는 복구 때 다시 검사한다. 현재 복구 실행은 적용 완료 상태이므로 `--apply`를 재실행하지 않는다. 개발용 `--apply --revise`는 원본 백업에서 재계산하고 직전 복구 해시와 일치하는 파일만 수정한다. 직전 정책 보고서도 보존한다. 파일별 교체여서 전체 디렉터리 트랜잭션은 아니므로 실행 중 배포하면 안 된다.

기존 단일 공급자 수집 스크립트는 복구 백업이 있으면 중단한다. 복구한 자료를 단순 재수집·이어붙이기로 덮어쓰는 것을 막기 위한 조치다. 새 데이터 실행은 기간·원본·정책을 따로 검증해야 한다.
