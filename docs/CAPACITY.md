# 데이터 용량 계획

종목을 계속 늘릴 계획이라, 얼마까지 괜찮고 한계에 닿으면 무엇을 하면 되는지 미리 정리해둡니다.

## 무엇이 늘어나고 무엇이 안 늘어나는가

| 대상 | 종목이 늘면 | 비고 |
|---|---|---|
| `data/stocks/*.json` | **비례해서 늘어남** | 유일하게 문제가 되는 부분 |
| `data/patterns/*.json` | **거의 그대로** | 사례를 패턴당 150건으로 상한을 두고 저장. 늘어나는 건 `count`·`stats` 숫자뿐 |
| `src/`, `vendor/` | 그대로 | 약 0.4 MB |

즉 신경 쓸 것은 `data/stocks/` 하나뿐입니다.

## 현재 수치 (format 2 기준)

- 캔들 1개 ≈ **48 바이트** (객체 형식이던 format 1 은 92 바이트였습니다)
- 종목 1개(2015년~현재, 약 2,900봉) ≈ **0.13 MB**
- 종목 121개(종목 117 + 지수 4) ≈ **16 MB**

`tools/fetch-data.ps1` 은 실행이 끝날 때마다 현재 용량과 200/500/1000개 기준 예상치를 출력합니다.

## 한계선

| 항목 | 한도 | 환산하면 |
|---|---|---|
| GitHub Pages 사이트 크기 | 1 GB | 종목 약 7,500개 |
| GitHub 저장소 권장 크기 | 1 GB (5 GB 부터 경고) | 위와 비슷 |
| 파일 1개 크기 | 100 MB | 종목 1개가 이 크기가 될 일은 없음 |
| Pages 월 대역폭 | 100 GB (소프트) | 아래 "전송량" 참고 |

**실질적인 목표선은 저장소 200 MB 이내 → 종목 약 1,500개.** 이 앱의 목적(학습용 통계)에는
수백 개면 충분하므로, 지금 구조로 한참 갑니다.

## 전송량은 걱정하지 않아도 됩니다

사용자 브라우저는 **한 번에 종목 하나만** 내려받습니다(`data.js` 가 선택 시점에 fetch).
게다가 GitHub Pages 는 JSON 을 gzip 으로 압축해 보내므로 실제 전송은 종목당 약 **25~30 KB** 입니다.
종목이 1,000개가 되어도 첫 화면 로딩은 지금과 똑같습니다.

전체를 한꺼번에 읽는 곳은 `tools/build-patterns.html` 하나뿐이고, 이건 배포본이 아니라
로컬에서만 돌리는 개발 도구입니다.

## git 이력이 커지는 문제

용량보다 실제로 신경 쓸 부분입니다. 데이터를 다시 받을 때마다 모든 파일이 새 blob 이 되면
`.git` 이 그만큼씩 불어납니다.

**대응: `-Append` 모드를 기본으로 쓰세요.**

```bash
powershell -ExecutionPolicy Bypass -File tools\fetch-data.ps1 -Append
```

기존 파일의 마지막 날짜 다음 봉만 받아서 뒤에 붙입니다. 파일의 앞부분이 그대로라
git 의 델타 압축이 잘 먹어서, 이력 증가분이 "새로 추가된 봉" 수준에 머뭅니다.
전체 재수집(`-Append` 없이)은 자릿수 규칙이나 수집 기간을 바꿨을 때만 하세요.

종목 몇 개만 추가할 때는:

```bash
powershell -ExecutionPolicy Bypass -File tools\fetch-data.ps1 -Only '005490.KS,LLY'
```

`-Only` 는 지정한 종목만 새로 받고 `index.json` 의 나머지 항목은 보존합니다.

## 한계에 가까워지면 쓸 수 있는 카드

위에서부터 비용이 싼 순서입니다.

1. **수집 시작 연도 늦추기** — `-From '2018-01-01'` 로 실행. 2015년 시작 대비 약 30% 감소.
   대신 통계 표본이 줄어듭니다.
2. **날짜를 정수로** — `"2015-01-02"`(12바이트) → `20150102`(8바이트). 캔들당 약 4바이트,
   전체의 8% 정도. `fields` 에 형식을 적어두었으므로 `data.js` 의 `expand()` 만 고치면 됩니다.
3. **종가 대비 델타 저장** — 절댓값 대신 전일 대비 변화량을 저장하면 자릿수가 크게 줄어
   30~40% 추가 절감이 가능합니다. 다만 디버깅이 어려워집니다.
4. **데이터를 별도 저장소로 분리** — 앱 저장소는 가볍게 두고 데이터는 다른 저장소나
   GitHub Release 에 올린 뒤 URL 로 읽습니다. 이때 CORS 설정이 필요합니다.
5. **기간 분할** — `{ticker}.2015-2019.json` 처럼 쪼개고 필요한 구간만 읽습니다.
   구현 비용이 가장 큽니다.

1번과 2번만 해도 지금 대비 절반 이하가 되므로, 4·5번까지 갈 일은 사실상 없습니다.

## 저장 형식 바꾸는 법

형식은 파일 안의 `format` 숫자로 구분합니다.

- `format` 없음 = 옛 객체 배열 형식 (그대로 읽힘)
- `format: 2` = 배열 행 + `fields` 순서

새 형식을 도입할 때는 `format: 3` 을 쓰고 `src/lib/data.js` 의 `expand()` 에 분기를 추가하세요.
앱의 나머지 코드는 항상 `{date, open, high, low, close, volume}` 객체만 봅니다.
